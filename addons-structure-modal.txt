Quero refatorar completamente a experiência de gerenciamento de Add-ons/Plugins do Metric.

Use as imagens anexadas como **referência visual e estrutural**, principalmente as telas do Playnite. Não quero uma cópia visual do Playnite. Quero reproduzir a mesma ideia de organização, hierarquia e fluxo, adaptada ao Design System atual do Metric.

## OBJETIVO PRINCIPAL

Hoje temos uma implementação de Add-ons que está ficando inconsistente porque existem dois padrões diferentes de configuração:

* DataSources
* Watchers

Além disso, informações de metadata do plugin ainda estão declaradas dentro das próprias classes TypeScript, por exemplo:

```ts
return {
  id: '@metric-org/discord-for-tests',
  name: 'Discord (Real IPC Observer)',
  version: '1.0.0',
  iconUrl: '...',
  description: 'Observador real do aplicativo Desktop do Discord via IPC Pipe',
}
```

Isso deve ser eliminado.

O projeto já possui um conceito de `manifest`, portanto **metadata de plugin deve vir exclusivamente do manifest**.

Também quero eliminar o modelo atual de configuração:

```ts
export interface ConfigField {
  id: string
  label: string
  type: 'text' | 'password' | 'url'
  required: boolean
  placeholder?: string
}

export interface FieldGroup {
  id: string
  label: string
  description?: string
  fields: ConfigField[]
}
```

Esse modelo é simples demais e não representa corretamente uma tela de configuração moderna.

Quero uma arquitetura genérica, tipada e extensível onde **qualquer plugin possa declarar suas próprias páginas/abas de configuração e seus próprios campos**, sem precisar criar componentes específicos no Add-ons Manager.

# 5. CONFIGURAÇÃO DE PLUGIN

A configuração de cada plugin deve ser **dinâmica e declarativa**.

Não quero criar manualmente um componente React específico para cada plugin.

Exemplo:

O plugin Redmine pode declarar:

General
Authentication
Synchronization
Advanced

Enquanto outro plugin pode declarar:

Connection
Filters
Notifications

Outro plugin pode ter apenas:

General

Cada plugin pode possuir suas próprias abas.

Portanto, NÃO faça algo como:

```tsx
if (plugin.id === 'redmine') {
  return <RedmineSettings />
}
```

Isso derrotaria o objetivo da arquitetura.

A UI deve ser gerada a partir de um schema tipado.

# 6. NOVO MODELO DE CONFIGURAÇÃO

Crie uma arquitetura semelhante conceitualmente a:

```ts
interface PluginSettingsSchema {
  tabs: PluginSettingsTab[]
}

interface PluginSettingsTab {
  id: string
  label: string
  description?: string
  fields: PluginSettingsField[]
}
```

Porém NÃO fique limitado ao modelo acima.

Quero que você projete uma solução realmente extensível.

Os campos precisam suportar, pelo menos:

* text
* password
* url
* number
* boolean
* select
* multi-select
* textarea
* secret
* path
* color
* date/time quando fizer sentido

E o modelo deve permitir evolução futura.

Por exemplo:

```ts
type PluginSettingsField =
  | TextField
  | PasswordField
  | NumberField
  | BooleanField
  | SelectField
  | MultiSelectField
  | TextareaField
  | ...
```

A tipagem deve ser discriminated union usando `type`.

Exemplo conceitual:

```ts
{
  id: 'serverUrl',
  type: 'url',
  label: 'Server URL',
  description: 'URL do servidor Redmine',
  required: true,
  placeholder: 'https://redmine.example.com'
}
```

Para select:

```ts
{
  id: 'syncInterval',
  type: 'select',
  label: 'Sync interval',
  options: [...]
}
```

Para boolean:

```ts
{
  id: 'enabled',
  type: 'boolean',
  label: 'Enable synchronization'
}
```

A arquitetura deve permitir adicionar novos tipos de campos sem quebrar os existentes.

Em `IOpenAPI.ts`, remover completamente o modelo atual:

```ts
export interface ConfigField {
  id: string
  label: string
  type: 'text' | 'password' | 'url'
  required: boolean
  placeholder?: string
}

export interface FieldGroup {
  id: string
  label: string
  description?: string
  fields: ConfigField[]
}
```

Não apenas renomeie as interfaces.

A arquitetura deve ser repensada.

Quero um modelo novo que represente:

Plugin
→ Settings Schema
→ Tabs
→ Sections (se necessário)
→ Fields

Por exemplo:

```text
PluginSettings
 ├── Tab
 │    ├── Section
 │    │    ├── Field
 │    │    └── Field
 │    └── Section

 │
 └── Tab
      └── Field
```

Sections devem ser opcionais.

Uma aba simples pode conter fields diretamente.

Uma aba complexa pode possuir sections.

# 11. SEPARAR RESPONSABILIDADES

Quero uma separação clara entre:

### Manifest

Responsável por identidade/metadata:

* id
* name
* version
* description
* icon
* author
* capabilities

### Plugin implementation

Responsável pela lógica:

* executar
* conectar
* sincronizar
* observar
* fornecer dados
* etc.

### Settings schema

Responsável por descrever como a configuração deve ser apresentada:

* tabs
* sections
* fields
* labels
* descriptions
* options
* validation metadata

### Settings renderer

Responsável por transformar o schema em componentes React.

### Settings storage

Responsável por persistir os valores.

Não misturar essas responsabilidades.

## PRINCIPAL DISTINÇÃO ARQUITETURAL

Quero que fique muito claro que existem duas coisas diferentes:

### 1. Add-ons Manager

É a infraestrutura de gerenciamento dos Addons.

Ele sabe que existem categorias como:

```text
DataSources
Watchers
Calendars
Punch
Themes
```

Essas categorias podem ser hardcoded.

### 2. Addon

É uma extensão concreta do Metric.

Exemplo:

```text
Redmine
Discord
Fake DataSource
Metric AI
```

Cada Addon possui seu próprio manifest e, quando necessário, seu próprio schema de configuração.

O Manager **não deve conhecer detalhes específicos de cada Addon**.

Por exemplo, o Manager não deve possuir:

```ts
if (addon.id === 'redmine') {
  // renderizar configuração do Redmine
}
```

A configuração deve vir declarativamente do próprio Addon.

A arquitetura final deve se aproximar de:

```text
Addon Manifest
      │
      ├── Metadata
      │
      ├── Capabilities
      │
      └── Settings Schema
              │
              ├── Tab
              │    ├── Section
              │    │    └── Field

                         │
                         ▼
                Addon Settings Renderer
                         │
```

O ponto importante é:

Isso mantém o Manager genérico sem criar abstrações desnecessárias para as categorias neste momento.
